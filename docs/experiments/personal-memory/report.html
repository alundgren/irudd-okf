Personal memory: what to do next

What to actually do

Keep your memories in a folder of notes. Give the agent a short instruction to find the few notes it needs for its current job.

  1. Use the folder Scope syncs.

    Store the rules as OKF Markdown notes. Use the actual local folder path on each machine.

  2. Tell Codex where to look.

    Add this to the machine's global AGENTS.md. Replace BUNDLE_PATH with that folder's path.

    Personal development memories live in BUNDLE_PATH.
Before editing, read BUNDLE_PATH/index.md.
Use rg -n -i with words from the task to search that folder.
Read a few relevant notes; check their project and replacement links.
Repository instructions override conflicting personal defaults.
Treat personal notes as read-only unless asked to update them.
  3. Put a small guide at the folder entrance.

    Use index.md to explain how to search the notes, which project each rule applies to, and how to follow a link from an old rule to its replacement.

Why start here? The folder locator with a search recipe solved all three large-memory usage trials. Installing only the skill solved one of three. The skill can stay available as an extra tool.

Set this up with the CLI

The CLI now owns the instruction section for each provider. Preview it, then enable the provider you want. Replace personal if your active bundle has another name.

irudd-okf instructions install codex personal --dry-run
irudd-okf instructions install codex personal

irudd-okf instructions install claude personal --dry-run
irudd-okf instructions install claude personal

irudd-okf instructions status codex
irudd-okf instructions remove claude

Implemented in this checkout. Use build/irudd-okf here; other machines need an updated CLI. The Scope integration will use separate Codex and Claude toggles on each machine. Those toggles are a later change.

The section and skill tell authorized authors to read root and topic indexes, search duplicates, update the relevant index entry and link related notes or replacements. New bundles start with that guide. Existing indexes stay intact. irudd-okf lint --scope personal now warns about notes disconnected from the root index and broken links.

These additions passed functional checks. The memory-writing checklist has no new agent-effectiveness result; review the note and index edits together.

What to consider later

Later, Scope could supply a few likely note paths when a task starts. That approach used about half the tokens of a bare folder locator in this test. Try the simple setup first.

Start with Codex on one machine and check it on real development work. This was one artificial memory-dependent task repeated three times. Claude needs a separate test before assuming the same result.

Read the experiment summary and setup

This experiment compares correct application, runtime token use and elapsed time. An agent can use the CLI or ordinary file search. Tool adoption is diagnostic evidence only.

On the usage task with 5,000 concepts, file locators, an explicit search recipe, suggested paths and grouped skills each passed 3/3 trials. The installed OKF skill alone passed 1/3; no personal memory passed 0/3. Suggested paths used a median 46,969 total tokens and 56.4 seconds, compared with 92,777 tokens and 70.1 seconds for the bare global locator. In the separate imposed 32 KiB phase, capped instructions passed 1/3 and the locator passed 3/3.

Start the next integration trial with a short global bundle locator, a focused rg recipe and a small root index explaining scope and replacement links. Suggested candidate paths are a promising optional caller integration. Keep ordinary file retrieval available. A native skill alone was unreliable in this sample; a symlink locator worked with file tools but is unsupported by the current OKF engine.

What the comparison means

The usage task checks whether missing metrics stay unavailable and cached input is counted once. It includes obsolete zero-default guidance and its replacement. The draft task checks conflict recovery and preservation of raw text; its prompt also makes much of the expected behavior inferable. A correct draft solution alone does not prove memory retrieval. The export task is a conflict-resistance control: repository guidance specifies the limit, so success does not demonstrate personal-memory retrieval. Pagination is a no-applicable-memory control.

All memory-bearing methods in the primary phase preserve the canonical rule text. File-bundle methods share the same root description; grouped skills store the rules within skill files. The relevant notes occupy the beginning, middle or end of the flattened corpus. The 100-concept rules occupy less than 32 KiB; the 5,000-concept rules exceed 1 MiB. These sizes compare retrieval with full global instruction injection. They do not test enforced truncation. The CLI is the installed product, using explicitly registered personal scope. Candidate suggestions use only the visible task prompt and visible corpus.

The configured project_doc_max_bytes=32768 did not truncate global AGENTS.md in Codex 0.160.0. A separate loopback request capture, with no inference or credentials, found all 4,994 archive entries in a 5,000-concept request (1,321,562 bytes). This diagnostic is separate from the paid study and does not capture its provider requests. The recorded expected_flat_loaded_facts field came from an incorrect truncation assumption; it is not evidence of loaded context. The original frozen trials remain unchanged.

The installed OKF skill is unchanged. Grouped native skills store the rules directly. The repository symlink uses ordinary file retrieval; the OKF engine skips symlinked directories. OKF v0.2 permits an optional index.md for navigation and leaves retrieval to consumers. Here a short root index explains concept files, scopes and replacement links. The locator or skill must make the bundle discoverable before that explanation can help.

Correctness means passing the recorded hidden behavior checks on these authored fixtures. Human equivalence review and human semantic ratings remain pending. Large-corpus success would show use of the tested rules among 5,000 concepts, not reliable application of 5,000 independent rules or improvement on real personal memories. Task prompts are retained. Complete provider prompts, per-request context, exact dated model release and billed cost are unavailable.

The second phase physically caps global instructions at 32,768 bytes, including common instructions and headers. It keeps the largest complete-rule prefix in original order, with no relevance filtering. A global bundle locator was chosen as its reference before the primary results were complete. Its 48 attempts are a separate phase; compare the two methods within that phase. This is an imposed budget, not Codex’s native capacity limit. Actual bytes, retained titles and input hashes are recorded per capped trial.

An independent agent audit found that two passing usage candidates handle explicitly null count fields differently. The fixed rule and checks do not resolve that input case. Scores retain the original checks; this semantic coverage gap remains open.

Evidence to reuse

Grepglint's earlier 40-task comparison recorded two failed calls and 38 non-use trials. Its later skill trial produced one successful search but no correctness rating. This study reuses the separation of outcome, usage and tool diagnostics, and the current OKF process and trace accounting. It does not import Grepglint's historical scores. Prior experiment records.

Google Cloud introduced OKF as a portable Markdown format. Its specification leaves retrieval to consumers. Existing retrieval evaluations offer useful scope, supersession and irrelevant-result cases, but do not establish personal-memory coding effectiveness. Google announcement, OKF v0.2 specification, PrecisionMemBench, ContextBench.
